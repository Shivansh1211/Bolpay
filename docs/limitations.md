# Known limitations

- All vendor names, phone numbers, and UPI IDs in this repository are fictional test data. The checkout and payment workflow use a mock gateway; these examples are not real merchant or customer records.

- Payments use the local mock gateway by default. Live Cashfree credentials, account settings, webhook registration, and callback verification have not been completed.
- OTP delivery is a development flow. Production SMS delivery and provider controls are not configured.
- OTP rate limits and failed-attempt tracking are process-local and reset on restart.
- `AttackSuiteTest.otpIsNotReturnedToClientByDefault` verifies the default API response and captured logs. Local E2E explicitly enables development OTP behavior for test registration.
- STOMP authentication and vendor topic isolation are verified locally over a signed JWT connection. This does not provide load, browser compatibility, or production infrastructure validation.
- Duplicate webhook handling is not exercised under concurrent delivery, and emitted WebSocket announcement counts are not asserted.
- Playwright covers the mock flow, live board updates, voice, and scheduled expiry. It is not a real-phone or live-provider test. The latest measured local webhook-received-to-board-DOM p95 was 70 ms across 20 samples; this is not a production performance guarantee.
- No hosting provider has been selected and no deployment has occurred.
- Render Free mock orders are held in process memory. A mock restart, sleep, or redeploy clears its order/session map, so a checkout link created before the mock sleeps may no longer work; recreate the demo order after wake. Render Free Postgres separately expires after 30 days, and the 750 free web-instance hours are shared across the workspace.
- A local Docker end-to-end run under a 512 MiB backend memory limit completed. Post-flow backend usage was 209.7 MiB of 512 MiB; this is a point-in-time post-flow reading, not a peak or a Render measurement.
- The local test runner uses a 5-second expiry to exercise real expiry quickly. Previously the backend container retained this setting after tests and could classify the mock's 5-second delayed callback as late. It now restores the normal 150-second expiry after a successful full run; after a failed run it must be reset manually. The latest successful full run verifies the mock delayed-payment classification under the short test expiry, not real-provider timing.
- Local database counts include test records and do not support a real-world late-payment rate. There is no vendor field study or soundbox comparison, so no win percentage is known.
- The user approved the design plan on 2026-11-05 and the live UI redesign is implemented. Quick amount and Mark as served remain preview-only examples.
- The wordmark uses Noto Sans Bold converted to SVG paths; Noto Sans Devanagari is the OFL companion. No font binaries are bundled.
- Registration supports an optional server-side `INVITE_CODE` gate. When unset, registration is open; when set, possession of the code is required but does not establish the invitee’s identity. Production must store/manage the code securely if this gate is desired.
- Duplicate-link handling returns a conflict and the UI asks for a new OTP after profile-save failures. The current full browser gate does not cover this duplicate-link recovery path. No comparative success percentage against a soundbox has been measured; the fake-app expiry test is one software simulation, not field evidence.
- A dedicated “Waking up the server…” state and safe retry/backoff behavior for sleeping hosts are not implemented.
- The current frontend lockfile audit reports 4 vulnerable package groups (npm package-group summary: 3 moderate, 1 high) across 11 advisory records. The direct React Router runtime package has two moderate advisories; Vite/esbuild findings are development/build-only. All audit-suggested remediations require major upgrades, so no dependency was changed to chase green. See [docs/npm-audit.md](npm-audit.md).
- The prototype is not production-ready and does not claim to prevent scams.
- Risk review is an asynchronous informational signal after order expiry. The backend sends ten numeric features; device identifiers are SHA-256 hashed before storage, and the typed scoring client only accepts numeric feature maps. ML does not authorize, reject, or change payment status. Local verification covers scorer-up/down/timeout behavior with unit tests and HTTP test servers; it is not a load or production-host test.
- When ML is unavailable or exceeds its 500 ms request timeout, the backend fallback flags an order only after the current device has at least three expired/late-paid orders within 15 minutes (`FRAUD_RULE_TIMEOUTS_15M`, default `3`). If a device identifier is absent, the per-device fallback cannot fire. Queue saturation can drop this best-effort review task while leaving expiry/payment state intact.
- The vendor board presents persisted review flags with plain-language reasons. A flag means “look at this order”; it does not establish fraud, identity, or intent. The seeded synthetic split reports Random Forest F1 0.995, Isolation Forest F1 0.801, and rule-baseline F1 0.883. Random Forest wins by F1 on this synthetic split, but production scoring currently uses Isolation Forest; synthetic results do not establish field performance. See `ml/reports/evaluation.md` and `ml/reports/metrics.json`.
- `seconds_to_first_attempt` currently measures time from the most recent recorded scan for the same hashed device and vendor to order creation. It is a proxy for scan-to-order latency, not measured time from scan to a payment attempt.
- The backend scorer's successful-response test uses a local HTTP fixture and a mocked flag repository; the end-to-end suite does not yet create a database-backed risk flag by calling the running Flask model and then assert its appearance on the browser board. The model image build trains/loads the model, but this specific live integration path remains unverified.
